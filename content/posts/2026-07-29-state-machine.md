在开发过程中，我们经常会遇到这样的逻辑：

- 订单可以是待支付、已支付、已发货或已完成；
- 一个网络请求可能处于空闲、加载中、成功或失败；
- 用户登录后可以浏览页面，退出后又会回到未登录状态；
- 游戏角色会在待机、移动、攻击和死亡之间切换。

这些逻辑刚开始很简单，但随着业务不断增加，代码往往会逐渐变成大量嵌套的 `if-else`：

```js
if (order.status === 'paid') {
  if (action === 'ship') {
    // 发货
  }
}
```

当状态和操作越来越多时，代码会变得难以理解，也很容易出现非法操作：已完成的订单不应该再次发货，未支付的订单也不应该直接退款。

这时，状态机提供了一种更清晰的解决方案。

## 什么是状态机？

状态机（State Machine）是一种描述系统行为的模型。它通常由三部分组成：

1. 状态：系统当前所处的阶段；
2. 事件：触发状态变化的操作；
3. 转换：从一个状态切换到另一个状态的规则。

可以把它简单表示为：

```text
当前状态 + 事件 = 下一个状态
```

以订单为例：

```text
待支付 --支付成功--> 已支付
已支付 --发货----> 已发货
已发货 --确认收货--> 已完成
```

状态机的核心思想是：系统在任意时刻都处于某个明确的状态，只有符合规则的事件才能触发状态变化。

## 一个简单的订单状态机

下面用 JavaScript 实现一个简单版本：

```js
class OrderStateMachine {
  constructor() {
    this.state = 'pending_payment';
  }

  transition(event) {
    const transitions = {
      pending_payment: { pay: 'paid' },
      paid: {
        ship: 'shipped',
        refund: 'refunded',
      },
      shipped: { receive: 'completed' },
    };

    const nextState = transitions[this.state]?.[event];

    if (!nextState) {
      throw new Error(
        `无法执行操作：当前状态为 ${this.state}，事件为 ${event}`
      );
    }

    this.state = nextState;
  }
}
```

使用时：

```js
const order = new OrderStateMachine();

order.transition('pay');
console.log(order.state); // paid

order.transition('ship');
console.log(order.state); // shipped

order.transition('receive');
console.log(order.state); // completed
```

如果尝试让已完成的订单再次发货，状态机会拒绝这次操作，而不是让系统进入一个不明确的状态。

## 状态机解决了什么问题？

### 限制非法状态转换

每个状态允许执行的操作都被明确写出，可以避免大量业务漏洞：待支付订单不能发货，已完成订单不能再次发货，已退款订单不能继续支付。

### 降低复杂度

状态机把复杂条件拆分成清晰的状态和转换规则，让每个状态的行为都更容易理解。

### 提高可维护性

新增状态时，只需要补充对应的转换关系，而不必在多个文件中修改条件判断。

### 更容易测试

状态机的测试通常非常直观：

```text
待支付 + 支付成功 = 已支付
已支付 + 发货 = 已发货
待支付 + 发货 = 非法操作
```

## 状态机并不只是一个状态变量

很多代码中都有类似这样的写法：

```js
let status = 'loading';
```

但只有一个状态变量，并不代表使用了状态机。

真正的状态机还需要明确：有哪些合法状态；每个状态允许接收哪些事件；每个事件会产生什么结果；哪些转换是不允许的；状态变化时是否需要执行额外动作。

换句话说，状态机关注的不只是“现在是什么状态”，更关注“接下来允许发生什么”。

## 状态机适合哪些场景？

状态机特别适合流程明确、状态有限、状态之间存在约束的场景，例如：

- 订单、支付和审批流程；
- 用户登录和表单提交；
- 网络请求和任务调度；
- 游戏角色行为；
- 前端页面交互。

如果一个模块中出现了大量状态判断、布尔变量组合或嵌套条件，就可以考虑是否应该引入状态机。

## 使用状态机时需要注意什么？

状态机也不是越复杂越好。使用时需要注意：

- 状态名称要清晰、稳定；
- 事件和状态要区分开；
- 不要让转换逻辑分散在多个地方；
- 对非法转换进行明确处理；
- 记录重要的状态变化，方便排查问题。

在大型项目中，也可以使用 XState 等专门的状态机库，让状态定义、事件处理和可视化更加规范。

## 总结

状态机的价值，不只是把 `if-else` 换成另一种写法，而是帮助我们用更明确的方式描述系统行为：

```text
系统当前处于什么状态？
它可以接收哪些事件？
这些事件会让它进入什么状态？
哪些操作必须被拒绝？
```

当业务流程开始变得复杂时，状态机可以让代码从“不断增加条件”转变为“明确描述规则”。

复杂的流程不一定需要更多代码，有时只需要更清晰的状态转换模型。
